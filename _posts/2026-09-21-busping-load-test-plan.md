# 1. 버스핑, 그리고 1차 MVP 완성

짬 내서 만들던 앱의 1차 MVP가 드디어 끝났다.

이름은 버스핑. 자주 타는 정류장을 즐겨찾기에 등록해두면, 그 근처에 갔을 때 "10번, 5분 후 도착 (3정거장 전)" 같은 푸시 알람이 자동으로 오는 앱이다.

앱은 즐겨찾기한 정류장 근처에 갔을 때만 서버에 위치를 보낸다. 서버는 그 요청 안에서 근처 즐겨찾기를 찾고, 공공 버스 API(TAGO)에서 도착 정보를 받아 FCM으로 알람을 쏘는 구조다.

이번 MVP에 들어간 기능은 디바이스 등록, 정류장 검색, 즐겨찾기, 도착정보 조회, 그리고 심장인 위치 기반 알람이다.

기능은 다 됐으니 이제 배포하면 되겠다 싶지만, 그 전에 이 서버가 실제로 유저를 받으면 얼마나 버틸 수 있는지 테스트로 확인해보고자 한다.

---

# 2. 목표는 유저 100명, 근데 뭘 어떻게 테스트하지?

목표는 미리 정해뒀다. 1차 MVP는 유저 100명. 100명이 앱을 켜놓고 쓰는 상황을 버티면 합격이라고 잡았다.

그런데 막상 테스트를 하려고 보니 막막하다. "100명을 버틴다"를 어떻게 테스트로 옮기지? 동시에 요청을 100개 쏘면 되는 건가, 초당 100개인가? 서버가 안 죽으면 통과인가, 응답이 10초씩 걸려도 안 죽기만 하면 되는 건가? 목표 숫자만 있고, 그걸로 뭘 재고 뭘 확인해야 하는지가 없다.

그리고 하나 더 걸리는 게 있다. 버스핑은 요청을 처리하는 길목마다 외부에 기대고 있다. 도착 정보는 공공 버스 API(TAGO)에서 오고, 알람은 FCM이 쏴준다. 정상일 때야 문제없겠지만 TAGO가 갑자기 느려지면? 아예 죽으면? 내 서버가 잘 만들어졌어도 남의 서버 때문에 무너질 수 있는 구조라, 이런 장애 상황도 꼼꼼히 확인하고 가야 한다.

정리하면 질문은 두 개다. 100명을 버티는지 어떻게 확인하나. 그리고 외부가 아플 때 나는 얼마나 아픈가. 이 두 질문을 하나씩 공부하면서 테스트 계획을 세워봤다.

---

# 3. 기준부터 정하자

고민하다 보니 순서가 잘못됐다는 걸 깨달았다. 테스트를 어떻게 돌릴지보다, 뭐가 통과인지를 먼저 정해야 했다.

찾아보니 이걸 정리해둔 개념이 이미 있었다. 바로 SLO(Service Level Objective)다. "우리 서비스는 이 정도 품질을 지키겠다"고 정해두는 목표 수치다. 이게 없으면 테스트를 돌려도 결과를 해석할 수가 없다. 서버가 안 죽었어도 응답이 10초씩 걸리면 유저 입장에선 죽은 거나 마찬가지니까, "안 죽음"이 아니라 "이 속도 안에서 응답함"이 기준이 되어야 한다.

<details class="callout" markdown="1">
<summary>SLO란?</summary>

Service Level Objective. 서비스가 지키기로 스스로 정한 품질 목표치다. "응답시간 p95 300ms 이하, 에러율 1% 미만"처럼 구체적인 숫자로 적는다.

비슷한 용어로 SLI(품질을 재는 지표 자체 - 응답시간, 에러율 같은 것)와 SLA(고객과의 계약 - 어기면 배상)가 있는데, 관계는 "SLI로 재고, SLO를 목표로 삼고, SLA로 약속한다".
</details>

그래서 버스핑의 기준을 정해봤다.

| 항목                            | 기준                  | 이유                                            |
| ----------------------------- | ------------------- | --------------------------------------------- |
| 일반 조회 API (즐겨찾기 목록, 정류장 검색 등) | p95 ≤ 300ms         | 화면 보면서 기다리는 요청. 즉각 떠야 한다                      |
| 위치 이벤트 API                    | p95 ≤ 3초            | 백그라운드 요청이라 여유는 있지만, 안에서 TAGO를 호출해서 느릴 수 있는 경로 |
| 에러율                           | 1% 미만               | 속도 지표의 사각지대 보완. 빨리 실패하면 p95는 오히려 좋아 보인다       |
| 알람 적시성                        | 위치 전송 → 푸시 도착 ≤ 5초  | 이 서비스의 존재 이유. 버스 놓치고 알람 오면 의미가 없다             |
| 가용성                           | 99.9% (월 중단 43분 이내) | 인스턴스 1대의 장애나 배포가 서비스 중단이 되면 안 된다              |

여기서 p95는 "요청 100개를 빠른 순으로 줄 세웠을 때 95번째 응답 시간"이다. 평균을 안 쓰는 이유는, 평균은 거짓말을 하기 때문이다. 요청 99개가 10ms고 1개가 10초면 평균은 110ms로 멀쩡해 보이지만, 유저 100명 중 1명은 10초를 기다렸다. p95는 "느린 쪽 유저의 경험"을 보는 지표다.

<details class="callout" markdown="1">
<summary>p95란?</summary>

95번째 백분위수(percentile). 응답시간을 빠른 순으로 줄 세웠을 때 95% 지점의 값으로, "요청 100개 중 95개는 이 시간 안에 응답했다"는 뜻이다.

p50(중앙값), p99도 같은 원리. 부하테스트에서 평균 대신 백분위수를 쓰는 이유는 소수의 극단값에 가려진 "느린 쪽 유저의 경험"을 봐야 하기 때문이다.
</details>

이제 "버틴다"가 정의됐다. 유저 100명이 쓰는 동안 위 기준을 전부 지키면 버티는 거다. 남은 건 "유저 100명이 쓰는 동안"을 실제 요청으로 만들어내는 일이다.

# 4. 유저 100명을 시나리오로 만들기

기준은 정했으니, 이제 "유저 100명이 쓰는 동안"을 만들 차례다. 그런데 유저 100명은 요청 몇 개일까?

처음엔 단순히 동시에 요청 100개를 쏘면 되는 줄 알았다. 근데 부하테스트는 그렇게 만드는 게 아니었다. 유저 100명이 같은 순간에 버튼을 누르는 게 아니라 각자 자기 흐름대로 앱을 쓰니까, **"유저의 행동 시나리오 × 유저 수"**로 트래픽을 만들어야 실제와 비슷한 부하가 된다.

그래서 버스핑 유저 1명의 흐름을 생각해봤다.

![버스핑 유저 시나리오](/assets/img/busping-user-flow.png)

1. 평소에는 아무 일도 없다. 앱은 유저가 즐겨찾기한 정류장 근처에 갔을 때만 서버에 위치를 알린다. 유저당 하루 몇 번, 출퇴근 시간에 몰리는 정도다.
2. 위치를 받은 서버가 알람을 보낸다. "10번, 5분 후 도착 (3정거장 전)".
3. 알람을 받은 유저가 앱을 연다. 도착정보 화면을 보면서 버스를 기다린다. 이때 화면이 실시간처럼 갱신되도록 앱이 30초마다 도착정보를 다시 조회한다. 버스가 올 때까지, 몇 분간.

이게 버스핑 유저의 한 사이클이다. 이 시나리오에 유저 100명을 태우는 게 곧 부하테스트가 된다. 이제 이 시나리오로 어떤 테스트를 돌릴지 정하면 된다.

---

# 5. 어떤 테스트를 해야 하나

시나리오는 만들었으니 이제 돌리면 되는데, 알아보니 부하테스트라는 게 한 종류가 아니었다. 목적마다 다른 테스트가 있고, 배포 전에 확인해야 할 것들을 정리하니 일곱 개가 나왔다.

| #   | 테스트      | 답하려는 질문                             |
| --- | -------- | ----------------------------------- |
| 1   | 베이스라인 측정 | 부하가 없을 때 각 API의 기준 수치는? (유저 1명)     |
| 2   | 로드 테스트   | 유저 100명을 SLO 안에서 버티나? (본편)          |
| 3   | 스트레스 테스트 | 한계는 몇 명이고, 한계에서 어떤 모양으로 무너지나?       |
| 4   | 스파이크 테스트 | 출근 시간처럼 트래픽이 순간에 몰리면?               |
| 5   | 소크 테스트   | 며칠씩 돌려도 새는 것(메모리·커넥션·디스크) 없나?       |
| 6   | 장애 상황 테스트 | TAGO가 느려지면? Redis가 죽으면? FCM이 실패하면?  |
| 7   | 가용성 테스트  | 인스턴스 1대가 죽어도, 배포 중에도 서비스가 되나?       |

1~5번은 첫 번째 질문("100명을 버티나")의 변주다. 기준 수치부터 재고(1), 목표를 버티는지(2), 여유는 얼마나 있는지(3), 몰릴 때(4)와 오래 돌 때(5)는 어떤지. 특히 스파이크는 버스핑에서 그냥 넘어갈 수 없는 게, 이 서비스의 트래픽은 하루 종일 균등한 게 아니라 **출근 시간 30분에 몰리는 게 본질**이라서다. 소크도 마찬가지로, 24시간 돌아갈 서버라면 세 시간짜리 테스트에 안 보이는 문제가 운영 3일 차에 터진다.

6~7번이 두 번째 질문("외부와 인프라가 아플 때")의 몫이다. 장애는 일부러 주입해본다. 진짜 TAGO를 느리게 만들 수는 없으니, 환경은 실제 그대로 두고 **외부 의존성만 지연·실패를 흉내내는 가짜로 갈아끼워서** 테스트한다.

순서에도 이유가 있다. 베이스라인이 맨 앞인 건 기준 없이는 비교가 안 되기 때문이고, 장애·가용성이 뒤인 건 **변수를 하나씩만 바꾸기 위해서다**. 정상 조건 통과를 먼저 확인해놔야, 장애 조건에서 무너졌을 때 그게 장애 때문이라고 말할 수 있다.

## 어디서 돌리나

전부 **실제 배포 환경에서** 돌린다.

> **로컬에서 돌리면 안 되는 이유**
>
> - **수치가 다르다** - 내 노트북에서 잰 300ms는 실제 서버의 300ms가 아니다. CPU도 네트워크도 운영과 다르다.
> - **네트워크 왕복이 빠진다** - DB가 같은 머신에 있으면 실제로는 존재하는 네트워크 왕복이 통째로 사라진다.
> - **가용성 테스트가 불가능하다** - 인스턴스를 죽여보는 테스트는 로드밸런서 없이는 아예 할 수 없다.

그래서 운영과 같은 구성(로드밸런서 + 서버 2대)을 클라우드에 띄우고, 부하는 그 밖에서 쏜다. 로컬의 역할은 테스트 스크립트가 제대로 도는지 확인하는 리허설까지고, 판정에 쓸 수치는 전부 배포 환경에서 나온 것만 믿기로 했다.

## 도구

**k6**를 쓰기로 했다. 유저 시나리오를 코드로 쓸 수 있고, SLO를 임계값(thresholds)으로 걸어두면 테스트가 끝날 때 통과/실패를 자동으로 판정해준다. 시나리오도 기준도 이미 만들어놨으니, 그대로 옮기기만 하면 된다.

# 정리

막막했던 "유저 100명을 버틸까"가 이제 실행 가능한 계획이 됐다. 기준(SLO) 다섯 개를 정했고, 유저의 행동을 시나리오로 만들었고, 배포 전에 돌릴 테스트 일곱 개와 순서를 정했다.

다음 글에서는 실제 배포 환경을 띄우고 이 계획을 하나씩 돌려본다.
