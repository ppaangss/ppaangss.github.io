## 개요

주소창에 URL을 치고 엔터를 누르면 페이지가 뜬다. 매일 수십 번씩 반복하는 일이고, 보통은 1초도 걸리지 않는다.

그런데 그 1초 안을 들여다보면 서로 다른 시스템 여럿이 릴레이로 움직이고 있다. 이름을 주소로 바꾸는 분산 시스템이 있고, 연결을 만드는 합의 절차가 있고, 암호화 협상이 있고, 그 위에서 비로소 요청과 응답이 오가고, 받은 텍스트를 픽셀로 바꾸는 작업이 마지막을 맡는다.

그래서 이번에는 엔터를 누른 순간부터 화면에 픽셀이 그려지기까지, 요청 하나의 여정을 처음부터 끝까지 따라가 본다.

![요청 한 번의 여정](/assets/img/url-to-rendering/url-to-rendering-01-journey-overview.png)

## 1. URL의 구조

브라우저가 가장 먼저 하는 일은 입력받은 문자열의 분해다. URL(Uniform Resource Locator)은 자원의 위치를 표기하는 형식이고, 각 부분이 여정의 서로 다른 단계에서 쓰인다.

```
https://www.example.com:443/search?q=network
```

| 부분 | 예시 값 | 역할 |
| --- | --- | --- |
| 스킴(scheme) | `https` | 통신에 쓸 프로토콜 |
| 호스트(host) | `www.example.com` | 요청을 받을 서버의 이름 |
| 포트(port) | `443` | 서버 안에서 요청을 받을 프로세스의 번호 |
| 경로(path) | `/search` | 서버 안에서 가리키는 자원의 위치 |
| 쿼리(query) | `q=network` | 자원에 함께 전달하는 매개변수 |

포트는 스킴마다 기본값이 정해져 있어 보통 생략한다. https는 443, http는 80이다.

분해가 끝나면 브라우저는 어디로(호스트와 포트), 어떻게(스킴), 무엇을(경로와 쿼리) 요청할지 알게 된다.

## 2. DNS 조회

분해로 얻은 호스트는 사람이 읽는 이름이다. 그런데 네트워크는 이름으로 패킷을 전달하지 못한다. 그러면 패킷은 무엇을 보고 목적지를 찾아가는가?

### IP 주소 (IP address)

IP 주소(IP address)란 네트워크에 연결된 장비를 식별하는 숫자 주소다. 요청을 받는 서버(server)도, 요청을 보내는 클라이언트(client)인 브라우저 쪽 장비도 각자 IP 주소를 가진다. 패킷은 이 숫자 주소로만 목적지를 찾아가므로, 이름을 IP 주소로 바꾸는 과정이 먼저 필요하다.

### DNS (Domain Name System)

DNS(Domain Name System)란 이름과 IP 주소의 대응을 관리하는 분산 시스템이다. 이 시스템에 이름을 물어 IP 주소를 받아 내는 과정이 DNS 조회(DNS resolution)다.

조회는 네트워크를 타기 전에 가까운 기록부터 뒤진다. 브라우저 자신의 DNS 캐시, OS의 캐시와 hosts 파일을 차례로 확인하고, 전부 비어 있을 때에야 리졸버(resolver)에 질의를 보낸다.

리졸버는 보통 ISP나 공용 DNS 서비스가 운영하는 서버다. 리졸버도 답을 모르면 루트 네임서버에서 시작하는 DNS 계층을 따라 내려가며 대신 답을 찾아 주는데, 이 방식의 질의를 재귀 질의(recursive query)라 한다. 찾은 답은 TTL(Time To Live) 동안 각 캐시에 남아, 같은 이름의 다음 조회는 네트워크를 타지 않는다.

## 3. TCP 연결 수립

IP 주소를 얻었으니 패킷을 보낼 수는 있다. 그런데 패킷을 목적지까지 전달하는 프로토콜인 IP(Internet Protocol)가 보장하는 것은 전달의 시도까지다. 패킷은 중간에 유실될 수 있고, 순서가 뒤바뀔 수도 있다.

HTML 문서를 받는 일에 이 수준의 보장은 부족하다. 바이트가 하나라도 빠지거나 순서가 섞이면 문서가 깨진다.

### TCP (Transmission Control Protocol)

TCP(Transmission Control Protocol)란 IP 위에서 신뢰성 있는 전송을 보장하는 프로토콜이다. 재전송과 순서 복원으로, 유실이 일어나는 네트워크 위에 "빠짐없이 순서대로 도착하는 바이트 스트림"을 만들어 준다.

이 보장을 시작하려면 양쪽이 먼저 합의해야 한다.

### 3-way 핸드셰이크 (3-way handshake)

3-way 핸드셰이크(3-way handshake)란 TCP 연결을 수립하는 세 번의 패킷 교환 절차다.

1. 클라이언트가 SYN 패킷으로 연결을 요청하며 자신의 시작 시퀀스 번호를 보낸다.
2. 서버가 SYN-ACK 패킷으로 수락하며 자신의 시퀀스 번호를 함께 보낸다.
3. 클라이언트가 ACK 패킷으로 확인하면 연결이 수립된다.

![3-way 핸드셰이크](/assets/img/url-to-rendering/url-to-rendering-02-three-way-handshake.png)

여기서 "연결"이라는 말의 실체를 짚을 필요가 있다. 두 장비 사이에 물리적인 전용선이 생기는 것이 아니다. 연결이란 양 끝의 OS가 각자 기억하기로 합의한 상태다. 상대의 주소와 포트, 주고받은 시퀀스 번호, 수신 버퍼 같은 정보를 양쪽이 유지하는 것이고, 그 사이에서 패킷을 나르는 네트워크 장비들은 연결의 존재를 모른다.

<details class="callout" markdown="1">
<summary>모든 통신이 연결을 만들지는 않는다</summary>
방금 전의 DNS 질의는 보통 TCP가 아니라 UDP(User Datagram Protocol)로 오간다. UDP는 핸드셰이크 없이 패킷을 하나 보내고 하나 받는 방식이라, 질문 하나에 답 하나로 끝나는 DNS 질의에는 연결 수립 비용이 없는 쪽이 적합하다.
</details>

## 4. TLS 핸드셰이크

TCP 연결 위로 바로 HTTP를 보내면 어떻게 될까. 패킷은 목적지까지 가는 동안 수많은 라우터와 중간 장비를 거치고, 그 경로 어디에서든 내용을 그대로 읽을 수 있다. 스킴이 http인 통신이 정확히 이 상태다.

스킴이 https였으므로 브라우저는 TCP 위에 한 겹을 더 올린다. TLS(Transport Layer Security)는 통신을 암호화하는 프로토콜이고, 본 통신 전에 TLS 핸드셰이크로 두 가지 문제를 해결한다.

### 1. 서버 인증

지금 연결된 상대가 정말 www.example.com인지 확인하는 단계다. 서버는 인증서(certificate)를 제시한다. 인증서는 "이 공개키는 이 도메인의 것이다"를 인증 기관(Certificate Authority, CA)이 서명한 문서이고, 브라우저는 내장된 신뢰 CA 목록으로 그 서명을 검증한다. 암호화만 하고 상대를 확인하지 않으면 공격자와의 암호화 통신이 성립할 수 있으므로, 인증이 암호화보다 먼저다.

### 2. 키 교환

이후의 통신을 암호화할, 둘만 아는 대칭키를 만드는 단계다. 키 교환(key exchange) 알고리즘은 도청자가 핸드셰이크 전체를 지켜봐도 결과 키를 계산할 수 없게 설계되어 있다. 핸드셰이크가 끝나면 이 연결 위를 지나는 모든 HTTP 메시지가 그 키로 암호화된다.

---

## 5. HTTP 요청과 응답

연결과 암호화가 준비됐고, 여기서부터가 여정의 본론이다. HTTP(HyperText Transfer Protocol)는 클라이언트가 요청(request)을 보내고 서버가 응답(response)을 돌려주는 요청-응답 구조의 프로토콜이다. 이 구조는 HTTP 버전이 바뀌어도 유지된다.

### 메서드 (method)

메서드(method)란 요청이 자원에 무엇을 하려는지 표현하는 동사다. 조회하는 GET과 제출하는 POST가 대표적이다. 요청의 첫 줄에 메서드와 경로가 실리고, URL에서 분해해 둔 경로와 쿼리가 이 자리에서 쓰인다.

### 상태 코드 (status code)

상태 코드(status code)란 서버가 응답의 첫 줄에 싣는, 요청 처리 결과를 나타내는 세 자리 숫자다. 첫 자리가 클래스를 나타낸다.

| 클래스 | 정의 |
| --- | --- |
| 2xx | 성공 (Successful) |
| 3xx | 리다이렉션 (Redirection) |
| 4xx | 클라이언트 오류 (Client Error) |
| 5xx | 서버 오류 (Server Error) |

상태 코드에 따라 지금까지의 여정이 통째로 반복되기도 한다. 리다이렉션 응답은 `Location` 헤더로 새 URL을 알려 주고, 브라우저는 그 URL로 여정을 다시 시작한다. 호스트가 바뀌면 DNS 조회부터 전부 다시 밟는다.

캐시는 반대로 여정을 생략한다. 이전 응답이 유효 기간 안에 브라우저 캐시에 남아 있으면 요청은 네트워크로 나가지도 않고, 유효 기간이 지났어도 조건부 요청으로 "바뀌었는가"만 물어서 안 바뀌었으면 본문 전송을 생략한다.

## 6. 브라우저 렌더링

응답 바디로 HTML이 도착했다. 네트워크의 일은 여기까지고, 이제 브라우저가 텍스트를 픽셀로 바꾼다.

이 변환은 렌더링 파이프라인(rendering pipeline)이라는 단계들을 거친다. HTML을 파싱해 문서 구조를 담은 DOM(Document Object Model) 트리를 만들고, CSS를 파싱해 스타일 규칙을 담은 CSSOM(CSS Object Model)을 만든다. 둘을 합쳐 화면에 그릴 요소만 남긴 렌더 트리를 만들고, 레이아웃(layout)에서 각 요소의 위치와 크기를 계산하고, 페인트(paint)에서 픽셀로 그리고, 합성(compositing)에서 그려진 레이어들을 한 화면으로 합친다.

파싱 도중 만나는 CSS 파일, 자바스크립트, 이미지는 각각이 또 하나의 HTTP 요청이다. 페이지 하나를 그리는 동안 지금까지의 여정이 리소스 수만큼 반복되는 셈이고, 이미 열어 둔 연결과 캐시가 그 반복의 비용을 줄인다.

---

## 7. 여정을 지도 위에: OSI 7계층

여정을 돌아보면 각 단계가 서로의 내부를 몰라도 됐다는 점이 눈에 띈다. TCP는 위에서 오가는 것이 HTTP인지 몰랐고, HTTP는 아래에서 패킷이 몇 번 재전송됐는지 몰랐다. 역할을 층으로 나누고, 각 층은 아래층의 서비스를 가져다 쓰면서 위층에 자기 서비스를 제공하는 구조다.

이 구조를 표준 참조 모델로 정리한 것이 OSI 7계층 모델(OSI 7-layer model)이다. 아래부터 물리(Physical), 데이터 링크(Data Link), 네트워크(Network), 전송(Transport), 세션(Session), 표현(Presentation), 응용(Application) 계층으로 역할을 나눈다. 실제 인터넷 프로토콜은 이보다 단순한 TCP/IP 4계층 모델(링크, 인터넷, 전송, 응용)로 분류할 때가 많고, OSI 모델은 역할을 말할 때의 공용 좌표로 쓰인다.

![OSI 7계층과 여정의 프로토콜](/assets/img/url-to-rendering/url-to-rendering-03-osi-layers.png)

지금까지 밟은 단계들을 이 지도에 놓으면 이렇게 된다.

| 여정의 단계 | 프로토콜 | OSI 계층 | TCP/IP 계층 |
| --- | --- | --- | --- |
| DNS 조회 | DNS | 응용 (7) | 응용 |
| 패킷 전달 | IP | 네트워크 (3) | 인터넷 |
| 연결 수립 | TCP | 전송 (4) | 전송 |
| 암호화 | TLS | 세션·표현 (5~6) | 전송과 응용 사이 |
| 요청과 응답 | HTTP | 응용 (7) | 응용 |

TLS처럼 깔끔하게 떨어지지 않는 칸도 있다. OSI 모델은 특정 프로토콜의 명세가 아니라 역할을 정리한 참조 모델이라, 실제 프로토콜이 계층 경계에 걸치는 일이 생긴다. 지도의 가치는 칸을 정확히 맞추는 데 있지 않고, 새 프로토콜을 만났을 때 "어느 계층의 일을 하는가"부터 물을 수 있게 되는 데 있다.

브라우저 렌더링은 이 지도에 없다. 렌더링은 네트워크가 배달을 마친 뒤 응용 프로그램 안에서 일어나는 일이라, 계층 모델의 바깥이다.

---

## 마무리

주소창의 엔터 한 번에서 출발해 URL 분해, DNS 조회, TCP 연결 수립, TLS 핸드셰이크, HTTP 요청과 응답, 렌더링까지 요청 하나의 여정을 시간 순으로 따라갔다. 각 단계는 서로 다른 문제를 하나씩 해결한다. 이름을 주소로 바꾸고, 유실이 일어나는 네트워크 위에 신뢰할 수 있는 바이트 스트림을 만들고, 그 통로를 암호화하고, 그 위에서 비로소 자원을 주고받고, 받은 문서를 픽셀로 바꾼다.

이 여정이 계층 구조 위에 놓인다는 것도 확인했다. 각 계층은 아래 계층의 보장을 전제로 자기 일만 하고, 그 분리 덕분에 한 계층의 내부를 몰라도 전체 흐름을 말할 수 있었다. 거꾸로 말하면 각 단계의 내부, 그러니까 재귀 질의가 실제로 거치는 네임서버들, 핸드셰이크 아래의 재전송과 흐름 제어, 인증서를 보증하는 신뢰 사슬, 픽셀이 되기까지의 파이프라인이 전부 이 지도 위의 서로 다른 칸에 들어 있다.
