## 인메모리 데이터 저장소

**인메모리 데이터 저장소(in-memory data store)** 는 데이터를 디스크가 아니라 주 메모리(RAM)에 두고 읽고 쓰는 저장소다.

MySQL이나 PostgreSQL 같은 전통적인 관계형 데이터베이스는 데이터의 원본을 디스크에 둔다. 자주 쓰는 데이터를 메모리에 캐시하기는 하지만, 쓰기는 결국 디스크에 기록되어야 완료된 것으로 본다. 반면 인메모리 저장소는 데이터의 원본이 메모리에 있다. 디스크는 필요할 때 백업 용도로만 쓴다.

이 차이가 중요한 이유는 저장 장치마다 접근 속도가 크게 다르기 때문이다. 하드웨어에 따라 다르지만 대략적인 규모는 다음과 같다.

| 저장 장치 | 임의 접근 지연 시간(대략) |
| --- | --- |
| RAM | 약 100나노초 |
| SSD | 수십~수백 마이크로초 |
| HDD | 수 밀리초 |

RAM은 SSD보다 수백 배 이상, HDD보다는 만 배 이상 빠르다. 따라서 데이터를 메모리에서 바로 꺼내면 디스크를 거칠 때보다 응답이 훨씬 빠르다.

단점도 있다.

첫째, RAM은 같은 용량의 디스크보다 비싸므로 저장할 수 있는 데이터 양이 제한된다. 둘째, RAM은 **휘발성(volatile)** 이다. 전원이 꺼지거나 프로세스가 종료되면 내용이 사라진다.

## Redis란?

**Redis(REmote DIctionary Server)** 는 키에 값을 연결해 저장하는 인메모리 **키-값 저장소(key-value store)** 다.

키-값 저장소는 모든 데이터를 키 → 값 쌍으로 다룬다. 키로 값을 찾는다는 점에서 프로그래밍 언어의 딕셔너리나 해시맵과 같다.


---

## Redis 특징

- **빠른 속도**: 데이터가 메모리에 있으므로 대부분의 명령이 1밀리초보다 훨씬 짧은 시간에 처리된다.
- **다양한 자료구조**: 값으로 단순한 문자열뿐 아니라 List, Hash, Set, Sorted Set 등을 저장할 수 있다. 서버가 자료구조를 직접 다루므로 "리스트 맨 앞에 추가", "점수 순으로 상위 10개 조회" 같은 연산을 명령 하나로 처리한다.
- **원자적 명령**: 각 명령은 다른 명령과 섞이지 않고 한 번에 실행된다. 여러 클라이언트가 같은 카운터를 동시에 올려도 값이 꼬이지 않는다.
- **선택적 영속성과 복제**: 필요하면 데이터를 디스크에 저장하고, 다른 서버로 복제할 수 있다.


이런 특징 때문에 Redis는 주 데이터베이스를 보조하는 역할로 많이 쓰인다. 대표적인 쓰임새는 다음과 같다.

| 쓰임새    | 설명                         |
| ------ | -------------------------- |
| 캐시     | 느린 DB 조회 결과를 잠시 저장해 두고 재사용 |
| 세션 저장소 | 여러 웹 서버가 공유하는 로그인 세션 저장    |
| 랭킹     | 점수 순 순위표                   |
| 처리율 제한 | API 호출 횟수 세기               |
| 메시지 큐  | 서비스 간 메시지 전달               |

반대로 Redis가 맞지 않는 경우도 있다. 메모리보다 훨씬 큰 데이터를 저장해야 하거나, 여러 테이블을 조인하는 복잡한 질의가 필요하거나, 단 한 건의 쓰기 유실도 허용할 수 없는 데이터라면 관계형 데이터베이스가 더 적합하다.

## 키 이름 규칙

**키(key)** 는 값을 찾기 위한 이름이다. Redis의 키는 바이너리 안전한 문자열이어서 어떤 바이트든 쓸 수 있고, 최대 512MB까지 허용된다. 하지만 실제로는 짧고 읽기 쉬운 키를 쓴다. 키가 길면 메모리를 더 쓰고 비교 비용도 늘어난다.

Redis에는 테이블이나 폴더가 없다. 모든 키가 하나의 평평한 공간에 놓인다. 그래서 키 이름 안에 구조를 담는 관례를 쓴다.

가장 널리 쓰이는 형식은 콜론(`:`)으로 구분하는 `객체타입:ID:필드` 형식이다.

```
user:1000:name        # 1000번 사용자의 이름
user:1000:email       # 1000번 사용자의 이메일
product:42:stock      # 42번 상품의 재고
session:a8f3c1        # 세션 ID a8f3c1의 세션 데이터
```

콜론에 특별한 기능이 있는 것은 아니다. Redis 서버는 `user:1000:name`을 그냥 하나의 문자열로 본다. 이 규칙의 가치는 사람이 키의 의미를 읽을 수 있고, 같은 종류의 키를 패턴으로 찾을 수 있다는 데 있다. 팀 안에서 한 가지 규칙을 정해 일관되게 쓰는 것이 중요하다.

키를 다루는 주요 명령은 다음과 같다.

| 명령 | 동작 | 반환값 | 예시 |
| --- | --- | --- | --- |
| `EXISTS key [key ...]` | 키가 있는지 확인 | 존재하는 키의 개수 | `EXISTS user:1000:name user:1000:email` → `2` |
| `DEL key [key ...]` | 키 삭제 | 삭제된 키의 개수 | `DEL user:1000:name` → `1` |
| `UNLINK key [key ...]` | 키를 목록에서 바로 지우고 메모리 해제는 백그라운드에서 처리 | 삭제된 키의 개수 | `UNLINK product:42:stock` → `1` |
| `TYPE key` | 값의 자료형 확인 | `string`, `list`, `none` 등 | `TYPE user:1000:email` → `string` |
| `RENAME key newkey` | 키 이름 변경(newkey가 있으면 덮어씀) | `OK` | `RENAME session:a8f3c1 session:b7e2d0` → `OK` |
| `DBSIZE` | 현재 데이터베이스의 키 개수 | 정수 | `DBSIZE` → `4` |
| `KEYS pattern` | 패턴에 맞는 모든 키 조회 | 키 목록 | `KEYS user:1000:*` → `user:1000:name`, `user:1000:email` |
| `SCAN cursor [MATCH pattern]` | 키를 조금씩 나눠 조회 | 다음 커서와 키 목록 | `SCAN 0 MATCH user:*` → `0`, `user:1000:name`, `user:1000:email` |

`DEL`과 `UNLINK`는 결과가 같지만, 아주 큰 값을 지울 때 `DEL`은 메모리를 해제하는 동안 서버를 붙잡아 둔다. `UNLINK`는 그 작업을 백그라운드로 넘긴다.

![DEL과 UNLINK, 큰 값의 메모리를 누가 해제하는지](/assets/img/redis-overview/redis-overview-01-del-vs-unlink.png)

`KEYS`는 `*`(아무 문자열), `?`(아무 한 글자) 같은 패턴을 쓸 수 있어 편리하지만, 모든 키를 한 번에 훑는다. 키가 수백만 개인 운영 서버에서 실행하면 그동안 다른 요청을 처리하지 못한다. 학습용 서버에서만 쓰고, 운영 환경에서는 `SCAN`을 쓴다.
