## 개요

터미널에서 `javac Main.java`로 컴파일하고 `java Main`으로 실행한다. 자바를 처음 배운 날부터 반복해 온 두 줄이고, 두 번째 줄을 치면 프로그램이 돈다.

그런데 이 두 줄 사이에는 건너뛴 질문이 있다. 컴파일러가 만든 .class 파일은 누가 읽는가? CPU가 바로 실행한다고 하기에는, .class는 CPU가 아는 형식이 아니다.

그래서 이번에는 `java Main`을 친 순간부터 코드가 CPU에서 돌기까지, .class 파일이 지나가는 경로를 따라가 본다.

---

## 1. CPU는 .class를 읽지 못한다

CPU가 실행할 수 있는 것은 기계어(machine code)뿐이다. 기계어는 CPU가 하드웨어로 알아듣는 명령어 집합(instruction set)이고, 이 집합은 아키텍처마다 다르다. x86 CPU와 ARM CPU는 서로 다른 명령어를 쓴다.

그래서 C 컴파일러는 소스 코드를 특정 CPU의 기계어로 바로 번역하고, x86용으로 컴파일한 실행 파일은 ARM에서 돌지 않는다. 플랫폼마다 다시 컴파일해야 한다.

javac는 다른 길을 간다. javac가 만드는 .class 파일에는 어떤 CPU의 기계어도 들어 있지 않다. 들어 있는 것은 바이트코드라는 제3의 형식이다. 그러면 어떤 CPU도 읽지 못하는 이 코드는 누가 실행하는가?

### JVM (Java Virtual Machine)

JVM(Java Virtual Machine)이란 바이트코드를 자신의 명령어 집합으로 삼는, 소프트웨어로 구현된 기계다. 물리 CPU가 기계어를 실행하듯 JVM은 바이트코드를 실행한다. 하드웨어가 아니라 OS 위에서 도는 하나의 프로세스이므로 가상 기계(virtual machine)라 부른다.

`java Main`을 치면 일어나는 일이 바로 이 기계의 기동이다. OS가 JVM 프로세스를 띄우고, JVM이 Main.class를 넘겨받아 실행을 시작한다. 결국 자바 코드가 CPU에 닿는 경로는 번역 두 번이다. javac가 소스 코드를 바이트코드로 바꾸고, JVM이 바이트코드를 그 자리의 기계어로 바꾼다.

![소스에서 CPU까지, 번역 두 번](/assets/img/jvm-internals/jvm-internals-01-two-translations.png)

## 2. 바이트코드, JVM의 명령어 집합

바이트코드(bytecode)란 JVM이 실행하는 명령어 집합이다. 명령 하나하나가 연산 코드(opcode) 1바이트로 시작해서 바이트코드라는 이름이 붙었다.

실체는 직접 열어볼 수 있다. 다음 코드를 컴파일하고,

```java
int a = 1;
int b = 2;
int c = a + b;
```

`javap -c Main`으로 .class 내부를 들여다보면 이 세 줄이 아래 명령들로 번역되어 있다.

```
0: iconst_1
1: istore_1
2: iconst_2
3: istore_2
4: iload_1
5: iload_2
6: iadd
7: istore_3
8: return
```

읽는 법은 단순하다. `iconst_1`은 상수 1을 스택에 올리고, `istore_1`은 스택 맨 위 값을 1번 지역 변수 칸에 내린다. `iload_1`과 `iload_2`는 두 변수를 다시 스택에 올리고, `iadd`가 둘을 꺼내 더한 결과를 올리고, `istore_3`이 그 결과를 3번 칸에 내린다. JVM은 이렇게 피연산자를 스택에 쌓아 계산하는 스택 기반 기계(stack machine)다.

여기서 "한 번 작성하면 어디서든 실행된다(Write Once, Run Anywhere)"가 해소된다. 바이트코드는 특정 CPU의 명령어가 아니라 JVM의 명령어이고, JVM은 OS·CPU 조합마다 그에 맞게 구현되어 배포된다. 같은 .class를 윈도우 x86의 JVM에 넣든 맥 ARM의 JVM에 넣든, 읽는 기계의 사양이 같으므로 결과도 같다. 이식성을 담당하는 것은 .class가 아니라 플랫폼마다 준비된 JVM이다.

## 3. 들어가기: 클래스 로더

JVM 프로세스가 떴다고 .class 파일이 저절로 메모리에 있는 것은 아니다. 디스크의 .class를 JVM 메모리로 들여오는 일을 맡는 부품이 따로 있다.

### 클래스 로더 (class loader)

클래스 로더(class loader)란 .class 파일을 찾아 읽고 JVM 메모리에 올리는 컴포넌트다. 작업은 세 단계를 거친다. 로딩(loading)이 파일의 바이트를 읽어 클래스 정보를 만들고, 링크(linking)가 바이트코드의 형식을 검증(verification)하고 static 변수의 자리를 기본값으로 준비(preparation)하고 다른 클래스를 가리키는 심볼릭 참조를 해석(resolution)하며, 초기화(initialization)가 static 변수 대입과 static 블록을 실행한다.

중요한 성질은 이 모든 일이 미리 일어나지 않는다는 점이다. 클래스는 처음 사용되는 시점에 로드된다. `java Main`은 Main 클래스를 올려 main 메서드를 실행할 뿐이고, 실행 중에 new로 다른 클래스를 처음 만나면 그때 그 클래스의 .class를 찾아 올린다. 그래서 클래스가 수천 개인 프로그램도 기동 시점에 전부 읽어들이는 비용을 내지 않고, 한 번도 안 쓰인 클래스는 끝까지 메모리에 올라오지 않는다.

<details class="callout" markdown="1">
<summary>클래스 로더의 계층</summary>
클래스 로더는 하나가 아니다. `java.lang.*` 같은 핵심 라이브러리를 올리는 부트스트랩 클래스 로더(bootstrap class loader), JDK의 나머지 모듈을 올리는 플랫폼 클래스 로더(platform class loader), 클래스패스의 사용자 코드를 올리는 애플리케이션 클래스 로더(application class loader)가 계층을 이룬다. 로드 요청은 부모에게 먼저 위임되는데(parent delegation), 핵심 클래스와 같은 이름의 클래스를 사용자가 만들어도 핵심 쪽이 먼저 로드되게 막는 구조다.

## 4. 자리 잡기: 런타임 데이터 영역

클래스 로더가 올린 코드와 프로그램이 만들어 낼 데이터는 각자 정해진 자리에 놓인다. 런타임 데이터 영역(runtime data area)이란 JVM이 프로그램 실행에 쓰는 메모리 전체의 구획이다.

영역은 다섯 개이고, 나뉘는 기준은 소유자다. 모든 스레드가 공유하는 영역이 둘, 스레드마다 하나씩 생기는 영역이 셋이다.

![런타임 데이터 영역의 지도](/assets/img/jvm-internals/jvm-internals-02-runtime-data-area.png)

### 1. 메서드 영역 (method area)

메서드 영역(method area)이란 클래스 로더가 올린 결과물이 놓이는 영역이다. 클래스의 구조 정보, 메서드의 바이트코드, 상수 풀(constant pool), static 변수가 여기 산다. 코드는 모든 스레드가 같은 것을 읽으므로 공유 영역이다.

### 2. 힙 (heap)

힙(heap)이란 new로 생성된 모든 객체와 배열이 할당되는 영역이다. 역시 모든 스레드가 공유한다. 그래서 여러 스레드가 같은 객체를 참조할 수 있고, 같은 이유로 공유 객체에는 동기화가 필요해진다.

객체는 쓰임이 끝나도 스스로 사라지지 않는다. 참조가 끊긴 객체를 찾아 회수하며 힙을 관리하는 것이 가비지 컬렉션(garbage collection)이다.

### 3. JVM 스택 (JVM stack)

JVM 스택(JVM stack)이란 메서드 호출의 기록이 쌓이는, 스레드마다 하나씩 생기는 영역이다. 메서드가 호출될 때마다 스택 프레임(stack frame) 하나가 쌓이고, 메서드가 끝나면 그 프레임이 걷힌다.

프레임 안에는 그 메서드의 지역 변수 배열(local variable array)과 피연산자 스택(operand stack)이 들어 있다. 앞에서 `istore_1`이 값을 내리던 1번 칸이 이 지역 변수 배열이고, `iadd`가 값을 꺼내던 스택이 이 피연산자 스택이다. 바이트코드 명령이 조작하던 공간이 전부 현재 프레임 안이었던 것이다.

스택이 스레드마다 따로라는 사실의 귀결이 지역 변수의 안전성이다. 지역 변수는 자기 스레드의 프레임 안에만 존재하므로, 힙의 객체와 달리 다른 스레드가 건드릴 방법 자체가 없다.

### 4. PC 레지스터 (PC register)

PC 레지스터(program counter register)란 스레드가 현재 실행 중인 바이트코드 명령의 주소를 담는 영역이다. `javap -c` 출력 왼쪽의 0, 1, 2가 바로 이 주소다. 스레드마다 하나씩 있어서 여러 스레드가 각자 다른 위치를 실행할 수 있고, 스레드가 CPU를 내줬다가 돌아와도 어디까지 실행했는지를 잃지 않는다.

### 5. 네이티브 메서드 스택 (native method stack)

네이티브 메서드 스택(native method stack)이란 자바가 아니라 C 등으로 구현된 네이티브 메서드를 실행할 때 쓰는 스택이다. 이것도 스레드마다 하나씩 생긴다.

## 5. 실행되기: 실행 엔진

코드가 메서드 영역에, 데이터 자리가 힙과 스택에 잡혔다. 남은 것은 실행이다. 실행 엔진(execution engine)이란 메서드 영역의 바이트코드를 읽어 실제 CPU 위에서 실행되게 만드는 컴포넌트다.

여기에는 선택지가 있다. 바이트코드를 한 줄씩 해석하면서 돌 것인가, 미리 기계어로 번역해 둘 것인가. JVM의 답은 둘 다 쓰는 것이다.

### 인터프리터 (interpreter)

인터프리터(interpreter)란 바이트코드를 한 명령씩 읽어 그 자리에서 해석해 실행하는 방식이다. 번역을 기다릴 필요가 없으므로 시작이 빠르다. 대신 같은 코드를 다시 만나도 해석 비용을 매번 다시 낸다. 루프가 수백만 번 돌면 같은 명령을 수백만 번 해석한다.

### JIT 컴파일러 (JIT compiler)

JIT 컴파일러(Just-In-Time compiler)란 자주 실행되는 바이트코드를 실행 도중에 기계어로 통째로 번역해 두는 컴파일러다. 번역된 기계어는 코드 캐시(code cache)에 저장되고, 그 다음부터 해당 코드는 해석 없이 기계어로 바로 돈다.

번역 자체에도 시간이 들기 때문에 모든 코드를 번역하지는 않는다. JVM은 메서드 호출 횟수와 루프 반복 횟수를 세고 있다가, 임계값을 넘은 코드만 골라 컴파일한다.

### HotSpot

HotSpot이란 OpenJDK와 오라클 JDK가 쓰는 JVM 구현의 이름이다. 이름이 바로 위 전략에서 왔다. 프로그램 실행 시간의 대부분은 소수의 뜨거운 지점(hot spot)에서 소모되므로, 전체를 인터프리터로 돌리면서 그 지점만 찾아 JIT로 집중 컴파일한다는 설계다.

컴파일에도 단계가 있다. 빠르게 번역하되 최적화는 가볍게 하는 C1 컴파일러와, 느리지만 강하게 최적화하는 C2 컴파일러를 코드의 뜨거움에 따라 단계적으로 거친다. 이를 티어드 컴파일(tiered compilation)이라 한다.

## 마무리

![JVM 전체 구조](/assets/img/jvm-internals/jvm-internals-03-full-structure.png)

`java Main` 한 줄에서 출발해 .class가 지나가는 경로를 끝까지 따라갔다. CPU는 .class를 읽지 못하므로 바이트코드를 명령어로 삼는 가상 기계가 있고, 그 기계 안에서 클래스 로더가 코드를 처음 쓰이는 시점에 메모리로 들여오고, 들여온 코드와 데이터가 런타임 데이터 영역의 다섯 칸에 자리 잡고, 실행 엔진이 인터프리터로 돌리다가 뜨거운 코드만 JIT 컴파일러로 기계어로 번역한다.

이 지도의 칸들은 성질을 하나씩 갖고 있다. 바이트코드가 JVM의 명령어라서 같은 .class가 어디서든 돌고, 힙이 공유 영역이라서 멀티스레드의 동기화 문제가 거기서 시작되고, JVM 스택이 스레드별이라서 지역 변수는 그 문제에서 면제된다. 자바의 많은 동작이 이 지도 위 어느 칸의 성질로 설명된다.
