## 코딩과 설계는 다른 종류의 문제다

알고리즘 문제는 정답이 있다. 시스템 디자인은 다르다. 같은 요구사항에서 서로 다른 설계 둘 다 옳을 수 있고, 같은 설계가 상황이 바뀌면 틀린 설계가 된다. 그래서 시스템 디자인의 산출물은 구조도 그 자체가 아니라 **"왜 이 구조인가"라는 선택의 근거**다. 

좋은 설계자를 가려내는 질문은 항상 같다 - "왜 그렇게 했어요? 다른 방법은 왜 안 했어요?"

## 요구사항을 두 종류로 쪼갠다

**1) 기능 요구사항 (Functional)** - 시스템이 *무엇을 하는가*.

"URL을 넣으면 짧은 URL을 돌려준다" 같은 것. 비교적 명확하다.

**2) 비기능 요구사항 (Non-functional)** - 시스템이 *어떤 품질로 하는가*. 설계를 실제로 결정하는 건 이쪽.

| 항목                    | 개념                                           | 판단 질문                            |
| --------------------- | -------------------------------------------- | -------------------------------- |
| **규모(Scale)**         | 시스템이 감당해야 하는 부하의 크기. 사용자 수, 요청량, 데이터량으로 표현된다 | 사용자 몇 명? 초당 요청 몇 건? 데이터 얼마나 쌓이나? |
| **지연 시간(Latency)**    | 요청을 보내고 응답을 받기까지 걸리는 시간                      | 응답이 100ms 안에 와야 하나, 3초여도 되나?     |
| **가용성(Availability)** | 시스템이 죽지 않고 정상 동작하는 시간의 비율                    | 1년에 몇 분까지 죽어도 되나?                |
| **일관성(Consistency)**  | 어디서 읽든 같은(최신) 데이터가 보이는 정도                    | 방금 쓴 데이터를 바로 읽어야 하나, 몇 초 늦어도 되나? |
| **내구성(Durability)**   | 한번 저장된 데이터가 장애가 나도 유실되지 않는 성질                | 데이터를 절대 잃으면 안 되나?                |

같은 "채팅 서비스"라도 사용자 1만 명이면 서버 한 대 + PostgreSQL로 끝이고, 1억 명이면 완전히 다른 시스템이다. **기능이 같아도 비기능이 다르면 다른 시스템이다.**

## 제약(Constraints): 설계는 주어진 조건 안에서의 선택이다

요구사항이 "원하는 것"이라면 제약은 "주어진 것"이다. 

- 물리 법칙 (네트워크 왕복은 시간이 든다, 디스크는 메모리보다 느리다)
- 돈 (서버 비용, 운영 인력)
- 시간 (출시 데드라인)
- 팀 (3명이 마이크로서비스 20개를 운영할 순 없다)

특히 **팀 크기와 운영 능력**은 자주 잊히는 제약인데, 실무에서는 기술적 우아함보다 이게 아키텍처를 더 자주 결정한다.

## 트레이드오프: 모든 선택은 무언가를 지불한다

시스템 디자인의 본질은 한 문장으로 요약된다.

**"얻는 게 있으면, 잃는 게 있다."**

| 기법 | 얻는 것 | 지불하는 것 |
|---|---|---|
| 캐시 | 빠른 응답 | 원본과 어긋날 수 있음(일관성), 무효화 로직 |
| 복제 | 읽기 확장, 내구성 | 복제 지연, 쓰기는 안 빨라짐 |
| 샤딩 | 쓰기 확장 | 조인·트랜잭션이 어려워짐 |
| 비동기 큐 | 급증 트래픽 흡수 | 순서 보장·디버깅·추적이 복잡해짐 |
| 마이크로서비스 | 독립 배포 | 네트워크 실패, 분산 트랜잭션, 운영 부담 |

트레이드오프는 "지금 지불할 필요가 있는가"라는 질문과 세트다. 트래픽이 서버 한 대로 충분한데 샤딩부터 하는 건 얻는 것 없이 대가만 지불하는 것. 따라서 핵심은 "필요해지기 전까지 단순하게"이고, 좋은 설계 문서에는 "지금은 X로 가지만, 트래픽이 N배가 되면 Y로 전환한다"는 **전환 조건**이 적혀 있다.

## 설계를 진행하는 표준 순서

1. **요구사항 명확화** - 기능/비기능을 캐묻는다. "얼마나 많은 사용자? 읽기가 많나 쓰기가 많나?"
2. **어림 계산** - QPS, 저장량을 대충 계산해서 "서버 한 대 문제인지 백 대 문제인지" 규모를 확정
3. **상위 설계** - 큰 박스들(클라이언트, LB, 서버, DB, 캐시)과 데이터 흐름을 그린다
4. **핵심 컴포넌트 깊이 파기** - 병목이 될 지점, 어려운 문제 한두 개를 골라 깊게 설계
5. **트레이드오프와 한계 명시** - 이 설계가 무엇을 포기했고 어디서 깨지는지 스스로 말한다

5번이 가장 차별화되는 단계. 자기 설계의 약점을 먼저 말하는 사람이 설계를 이해한 사람이다.
