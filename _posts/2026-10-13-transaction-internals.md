## 개요

계좌 이체는 UPDATE 두 번이다. 내 계좌에서 돈을 빼는 문장이 하나, 상대 계좌에 돈을 넣는 문장이 하나 필요하다. 그런데 첫 번째 UPDATE가 끝난 직후 서버가 죽으면 어떻게 될까. 내 잔액은 줄었는데 상대 잔액은 그대로인, 한쪽 갱신만 반영된 상태로 남는다. 두 계좌의 합이 맞지 않는 심각한 문제가 발생하는 것이다.

데이터베이스는 이런 사고를 막는 장치를 기본으로 제공한다. 

트랜잭션(transaction)이다. 단어 자체는 많이 들어봤고 "전부 성공 아니면 전부 취소"라는 정의도 알고 있었다. 그런데 정작 그게 왜 가능한지, 데이터베이스가 안에서 무엇을 하길래 "전부 취소"가 되는지는 설명하지 못했다. 그래서 이번에는 트랜잭션의 개념에서 출발해서, ACID라는 성질 정리를 거쳐, 그 성질이 실제로 구현되는 메커니즘인 undo 로그와 redo 로그까지 내려가 봤다.

---

## 트랜잭션이 왜 필요한가

위의 계좌 이체를 SQL로 쓰면 이렇다.

```sql
UPDATE account SET balance = balance - 10000 WHERE id = 'me';
UPDATE account SET balance = balance + 10000 WHERE id = 'you';
```

문제는 이 두 문장이 데이터베이스 입장에서는 아무 관계가 없는 별개의 명령이라는 점이다. 첫 문장이 반영된 뒤 두 번째 문장이 실행되기 전에 서버가 죽거나, 두 번째 문장이 제약 조건 위반으로 실패하면, 데이터베이스에는 첫 문장의 결과만 남는다. 출금만 되고 입금은 안 된 상태다.

사람에게 계좌 이체는 하나의 작업이다. 출금과 입금이 따로 성공하는 경우는 없어야 한다. 이렇게 업무 관점에서 더 쪼갤 수 없는 작업 묶음을 논리적 작업 단위(logical unit of work)라고 부르고, 트랜잭션은 이 논리적 작업 단위를 데이터베이스에 알려주는 수단이다. 트랜잭션으로 묶인 문장들은 하나의 단위로 처리된다. 전부 반영되거나, 하나라도 실패하면 전부 없던 일이 된다.

전부 반영하는 것을 커밋(commit), 전부 취소하는 것을 롤백(rollback)이라고 한다.

---

## 트랜잭션의 동작 흐름

트랜잭션의 경계는 세 가지 명령으로 정한다. 

시작을 선언하는 BEGIN(또는 START TRANSACTION), 확정하는 COMMIT, 취소하는 ROLLBACK이다. 

계좌 이체에 적용하면 이렇게 된다.

```sql
BEGIN;
UPDATE account SET balance = balance - 10000 WHERE id = 'me';
UPDATE account SET balance = balance + 10000 WHERE id = 'you';
COMMIT;
```

BEGIN과 COMMIT 사이의 변경은 아직 확정이 아니다. 중간에 문제가 생기면 ROLLBACK으로 BEGIN 이전 상태로 돌아갈 수 있고, 커밋 전에 서버가 죽어도 데이터베이스가 재시작하면서 알아서 되돌린다. COMMIT이 실행된 순간에만 변경이 확정된다.

그런데 평소에 콘솔에서 UPDATE 한 줄을 날리면 BEGIN도 COMMIT도 없이 바로 반영된다. 트랜잭션 없이 실행된 것일까?

### 자동 커밋 (autocommit)

자동 커밋(autocommit)이란 문장 하나가 실행을 마칠 때마다 데이터베이스가 그 문장을 트랜잭션 하나로 취급해 즉시 커밋하는 모드다.

MySQL을 비롯한 대부분의 데이터베이스는 이 모드가 기본값이다. 트랜잭션이 없는 실행이란 애초에 존재하지 않고, 묶음의 크기를 내가 정하느냐 문장 단위로 자동으로 정해지느냐의 차이만 있을 뿐이다.

그래서 여러 문장을 하나로 묶고 싶을 때만 BEGIN으로 자동 커밋을 잠시 멈추고 경계를 직접 선언하는 것이다.

## ACID, 트랜잭션이 보장하는 네 가지 성질

트랜잭션이 보장하는 성질은 네 가지로 정리되어 있고, 각 성질의 영문 첫 글자를 따서 ACID라고 부른다.

### 1. 원자성 (Atomicity)

트랜잭션 안의 작업은 전부 반영되거나 전부 취소된다. 중간까지만 반영된 상태는 존재할 수 없다. 계좌 이체에서 출금만 되는 사고를 막는 성질이 바로 이것이다.

### 2. 일관성 (Consistency)

트랜잭션이 끝난 뒤에도 데이터베이스는 정해진 규칙을 만족하는 상태여야 한다. 잔액은 음수가 될 수 없다는 제약 조건(constraint)이 있다면, 트랜잭션은 그 규칙이 깨진 상태로 끝날 수 없다. 규칙을 깨는 트랜잭션은 롤백된다.

### 3. 격리성 (Isolation)

동시에 실행되는 트랜잭션들은 서로의 중간 상태를 보지 못해야 한다. 내 이체가 진행되는 도중의 어중간한 잔액을 다른 트랜잭션이 읽으면 안 된다. 격리수준(isolation level)이 바로 이 격리성의 자리다. 격리를 완벽하게 하면 동시 처리 성능이 떨어지기 때문에, 격리수준은 이 성질을 어디까지 엄격하게 지킬지를 단계로 나눠 거래하는 장치다. ACID의 네 성질 중 유일하게 강도 조절이 공식화되어 있는 성질인 셈이다.

### 4. 지속성 (Durability)

커밋된 트랜잭션의 결과는 영구적이다. 커밋 직후에 서버가 죽고 정전이 나도, 재시작한 데이터베이스에는 그 결과가 남아 있어야 한다.

네 성질은 구현 주체가 갈린다. 원자성과 지속성은 데이터베이스가 로그로 직접 구현하는 성질이고, 격리성은 락과 MVCC로 구현된다. 일관성은 조금 다른데, 나머지 세 성질과 제약 조건 위에서 애플리케이션이 올바른 로직을 짰을 때 결과로 얻어지는 성질에 가깝다.

## 원자성의 구현, undo 로그와 롤백의 실체

롤백은 변경을 전부 취소한다. 그런데 데이터베이스가 시간을 되돌릴 수는 없다. 이미 바뀐 값을 되돌리려면 바꾸기 전 값을 어딘가에 적어뒀어야 한다.

그 기록이 undo 로그(undo log)다. 트랜잭션이 데이터를 변경하기 직전에, 데이터베이스는 변경 전의 값을 undo 로그에 먼저 기록한다. 잔액을 50000에서 40000으로 바꾸는 UPDATE라면, "이 행의 balance는 원래 50000이었다"는 기록이 먼저 남고 그다음에 값이 바뀐다.

롤백은 이 로그를 역순으로 읽으면서 반대 연산을 실행하는 것이다. UPDATE로 바꾼 값은 원래 값으로 되돌리는 UPDATE를, INSERT로 넣은 행은 DELETE를, DELETE로 지운 행은 다시 INSERT를 실행한다. 즉 롤백은 undo 로그를 보고 역연산을 수행하는 또 하나의 실행이다. 트랜잭션이 커밋되지 못하고 죽어도 undo 로그만 살아 있으면 언제든 원상 복구가 가능하므로, 원자성은 이 로그 하나로 보장된다.

undo 로그의 역할은 롤백이 전부가 아니다. 어떤 트랜잭션이 값을 바꾸는 동안 다른 트랜잭션이 같은 데이터를 읽으면, 데이터베이스는 undo 로그에 남아 있는 변경 전 값을 보여줄 수 있다. 변경 이력이 곧 과거 버전의 저장소가 되는 것이고, 이 메커니즘이 MVCC(Multi-Version Concurrency Control)다.

## 지속성의 구현, redo 로그와 WAL

이번에는 반대 방향의 질문이다. COMMIT이 성공으로 응답한 직후 정전이 났다면, 그 변경은 살아 있을까. 지속성이 보장되려면 살아 있어야 한다. 그러려면 커밋 시점에 변경이 디스크 어딘가에 반드시 내려가 있어야 한다. 메모리는 전원이 꺼지면 사라지기 때문이다.

가장 단순한 방법은 커밋할 때마다 변경된 데이터 페이지를 전부 디스크에 쓰는 것이다. 하지만 트랜잭션 하나가 건드리는 행들은 디스크 여기저기에 흩어져 있어서, 이 방식은 매 커밋마다 랜덤 I/O(random I/O)를 일으킨다. 느려서 쓸 수 없다.

![랜덤 I/O vs 순차 I/O](/assets/img/transaction-internals/transaction-internals-01-random-vs-sequential-io.png)

그래서 데이터베이스는 로그를 하나 더 쓴다. redo 로그(redo log)다. undo 로그가 변경 전 값을 적는다면, redo 로그는 변경 후 내용을 적는다. 어느 페이지의 어느 위치를 어떤 값으로 바꿨는지를 기록하는 것이다. 커밋 시점에 디스크에 내려가는 것은 데이터 페이지가 아니라 이 redo 로그다. 로그는 파일 끝에 이어 쓰기만 하면 되는 순차 I/O(sequential I/O)라서 랜덤 I/O보다 훨씬 빠르다. COMMIT은 redo 로그가 디스크에 동기화되는 것을 확인한 뒤에야 성공을 응답한다.

실제 데이터 파일 반영은 커밋과 분리된다. 변경은 일단 메모리 위의 데이터 페이지에만 적용해 두고, 디스크의 데이터 파일에는 나중에 백그라운드에서 모아서 쓴다. 이렇게 데이터 파일보다 로그를 먼저 쓰는 방식을 WAL(Write-Ahead Logging)이라고 한다. 커밋 직후 정전이 나서 메모리의 변경이 날아가도 문제가 없다. 재시작한 데이터베이스가 디스크에 남은 redo 로그를 처음부터 다시 적용하면(roll forward) 커밋된 변경이 전부 재현되기 때문이다.

복구 과정에는 undo 로그도 함께 쓰인다. redo 로그에는 커밋되지 못한 트랜잭션의 변경도 섞여 있을 수 있어서, 복구는 두 단계로 진행된다. 먼저 redo 로그를 재적용해서 장애 직전 상태를 만들고, 그다음 undo 로그로 커밋되지 않은 트랜잭션들을 롤백한다. redo가 지속성을, undo가 원자성을 맡는 분업이 복구 과정에서 그대로 드러난다.

## 커밋 한 번에 일어나는 일

여기까지 공부한 내용을 계좌 이체 트랜잭션 하나의 일생으로 다시 꿰면 이렇다.

![커밋 한 번에 일어나는 일](/assets/img/transaction-internals/transaction-internals-02-commit-flow.png)

BEGIN 이후 첫 UPDATE가 실행되면, 데이터베이스는 변경 전 잔액을 undo 로그에 기록하고, 메모리 위의 데이터 페이지에서 값을 바꾸고, 그 변경 내용을 redo 로그에 기록한다. 두 번째 UPDATE도 같은 과정을 밟는다. 이 시점까지 디스크의 데이터 파일은 그대로다.

COMMIT이 실행되면 데이터베이스는 redo 로그를 디스크에 동기화하고, 그것이 확인된 순간 성공을 응답한다. 변경된 데이터 페이지는 나중에 백그라운드에서 디스크로 내려간다.

중간에 ROLLBACK이 실행되거나 서버가 죽으면, undo 로그의 역연산으로 변경 전 상태가 복원된다. 커밋 이후에 서버가 죽으면, 재시작 시 redo 로그 재적용으로 변경이 되살아난다. 어느 시점에 무너져도 "전부 아니면 전무"와 "커밋은 영원하다"가 지켜지는 이유가 이 두 로그다.

## 마무리

트랜잭션을 "전부 성공 아니면 전부 취소"라는 정의로만 알고 있다가, 이번에 그 보장이 공짜가 아니라는 것을 알게 됐다. 모든 변경의 전 값을 적는 undo 로그와 모든 변경의 후 내용을 적는 redo 로그, 이 둘을 항상 쓰고 있기 때문에 롤백도 복구도 가능한 것이었다. 롤백은 undo 로그를 읽어 수행하는 역연산 실행이고, COMMIT의 응답은 데이터 파일이 아니라 redo 로그의 디스크 동기화를 기다린다.

ACID 중 원자성과 지속성의 구현을 따라 내려갔고, 격리성은 격리수준이라는 이름으로 그 자리만 확인했다. undo 로그는 롤백의 재료이면서 동시에 MVCC의 버전 저장소다. 격리성은 이 버전들 위에서 동작한다.
