시스템 디자인 대화에서 "빠르다", "안정적이다"는 말은 아무 정보가 없다. 숫자로 말하는 어휘 두 벌이 필요하다. 하나는 **돌아가는 시스템을 읽는 지표**(지연, 처리량, 백분위수, 가용성), 다른 하나는 **설계하기 전에 규모를 확정하는 어림 계산**.

## 처리량과 지연 시간은 다른 축이다

- **지연 시간(Latency)**: 요청 하나가 응답받기까지 걸리는 시간(ms). *사용자 한 명의 경험*.
- **처리량(Throughput)**: 단위 시간에 처리하는 요청 수(QPS). *시스템 전체의 용량*.

고속도로 비유가 정확하다. 지연은 "입구에서 출구까지 걸리는 시간", 처리량은 "시간당 통과 차량 수". 차로를 늘리면(수평 확장) 처리량은 늘지만 개별 차가 빨라지진 않는다. 제한속도를 올리면(성능 최적화) 지연은 줄지만 용량이 느는 건 아니다. **따로 측정하고 따로 개선한다.**

둘 사이에 연결고리가 하나 있다. 부하가 용량에 가까워지면 큐가 쌓이며 **지연이 갑자기 치솟는다**. 처리량 그래프는 멀쩡한데 지연이 폭발하는 지점이 시스템의 실질 한계고, 성능 테스트에서 찾는 게 바로 이것이다.

![사용률이 높아질수록 지연이 폭발하는 곡선](/assets/img/performance-metrics-and-estimation/system-design-04-utilization-latency.png)

## 평균은 거짓말을 한다: 백분위수

응답 99개가 100ms, 1개가 10초라면 평균은 199ms, **아무도 경험하지 않은 숫자**다. 응답 시간은 정렬해놓고 위치로 읽는다.

- **p50 (중앙값)**: 절반이 이보다 빠름. 보통 경험
- **p95**: 20명 중 1명은 이보다 느린 경험
- **p99**: 100명 중 1명이 겪는 나쁜 경험. 꼬리 지연(tail latency)

![응답 시간 분포와 p50, p95, p99, 그리고 꼬리에 끌려간 평균의 위치](/assets/img/performance-metrics-and-estimation/system-design-03-latency-percentiles.png)

왜 꼬리에 집착하는가:

1. **느린 요청을 겪는 사람이 제일 중요한 고객일 수 있다.** 데이터가 많은 사용자 = 헤비 유저 = 돈 내는 사용자의 요청이 무겁다. 아마존이 p99.9까지 보는 이유.
2. **꼬리는 증폭된다.** 화면 하나에 백엔드 호출이 100번이면, 각 호출이 p99를 피할 확률이 99%여도 전부 피할 확률은 0.99¹⁰⁰ ≈ 37%. 사용자의 63%가 최소 한 번은 p99를 맞는다. MSA처럼 호출이 퍼지면 p99가 곧 평균 체감이 된다.

## 가용성은 9가 몇 개인가

| 가용성     | 연간 허용 다운타임 | 감각         |
| ------- | ---------- | ---------- |
| 99%     | ~3.65일     | 취미 프로젝트    |
| 99.9%   | ~8.8시간     | 일반 서비스     |
| 99.99%  | ~53분       | 유료 SaaS 수준 |
| 99.999% | ~5.3분      | 통신/금융 인프라  |

1. **9 하나마다 비용이 곱으로 뛴다.** 99.9%까지는 "장애 나면 사람이 고친다"로 되지만 99.99%부터는 자동 복구가 필수다(연간 53분 안에 사람이 못 일어난다). 99.999%는 배포·장애·점검 전부 무중단이어야 한다. "정말 9가 몇 개 필요한가?"는 트레이드오프 질문 그 자체.
2. **직렬 의존은 가용성을 깎는다.** 99.9%짜리 서비스 3개를 직렬로 거치면 0.999³ ≈ 99.7%. 시스템은 약한 고리들의 곱으로 나빠진다. 반대로 병렬(둘 중 하나만 살아도 됨)로 두면 9가 늘어난다. 이중화(redundancy)의 수학적 근거.

## SLI / SLO / SLA

- **SLI** (Indicator): 실제 측정값. "지난 30일 p99 = 280ms"
- **SLO** (Objective): 내부 목표. "p99 < 300ms를 99.9% 시간 동안 유지"
- **SLA** (Agreement): 고객과의 계약. 어기면 배상. 보통 SLO보다 느슨하게 잡는다(내부 목표는 빡빡하게, 약속은 여유 있게).

SLO의 실전 용법은 **에러 버짓(error budget)**이다. 목표가 99.9%면 한 달에 ~43분은 실패해도 되는 예산이다. 예산이 남으면 공격적으로 배포하고, 소진했으면 신기능을 멈추고 안정화한다. "안정성 vs 개발 속도" 논쟁을 숫자로 정리하는 도구.

## 설계 전에 규모부터 확정하는 어림 계산

지표가 돌아가는 시스템을 읽는 어휘라면, 어림 계산(back-of-envelope)은 **설계하기 전에** 쓰는 도구다. 요구사항을 들었으면 그림 그리기 전에 "서버 한 대짜리 문제인가, 백 대짜리 문제인가"를 숫자로 확정한다. 목적은 정밀함이 아니라 **자릿수(order of magnitude)**. 3,472 QPS와 5,000 QPS는 같은 설계고, 5,000과 500,000은 다른 설계다.

### 외워둘 기준 숫자

**시간**
- 하루 ≈ 86,400초 ≈ **10만 초** (그냥 10⁵로 쓴다)
- 한 달 ≈ 250만 초, 1년 ≈ 3,000만 초

**크기**
- 2¹⁰ ≈ 천(KB), 2²⁰ ≈ 백만(MB), 2³⁰ ≈ 십억(GB). 저장량 계산은 이 근사로 충분하다

**접근 속도의 사다리**

| 작업              | 시간     | 감각                 |
| --------------- | ------ | ------------------ |
| 메모리 읽기          | ~100ns | 기준점                |
| SSD 랜덤 읽기       | ~100µs | 메모리의 **1,000배** 느림 |
| 같은 데이터센터 내 네트워크 왕복 | ~0.5ms |                    |
| HDD 탐색          | ~10ms  |                    |
| 서울 ↔ 미국 서부 왕복   | ~150ms | 빛의 속도는 협상 불가       |

여기서 설계 직관 두 개가 나온다:

1. **메모리 vs 디스크는 1,000배 게임**. 그래서 캐시가 효과를 낸다.
2. **대륙 간 왕복은 물리 법칙**. 최적화로 못 없앤다. 데이터를 사용자 가까이 두는 것(CDN, 리전 분산)만이 답.

**단일 장비의 대략적 용량** (자릿수 감각)
- 웹 서버 한 대: 단순 요청 기준 초당 수천 건
- PostgreSQL/MySQL 한 대: 초당 수천 쓰기
- Redis 한 대: 초당 ~10만 연산
- 서버 한 대 메모리: 수십~수백 GB

### 변환 공식

```
QPS ≈ DAU × 1인당 하루 요청 수 ÷ 100,000(초)
피크 QPS ≈ 평균의 2~5배

하루 저장량 ≈ 하루 생성 건수 × 건당 크기
총량 ≈ 하루 저장량 × 보존 일수 (× 복제본 수)
```

건당 크기 감각: 텍스트 레코드 수백 B~1KB, 사진 수백 KB, 동영상 수십 MB.

### 계산 연습 해보기 (트위터급 서비스)

DAU 1억, 1인당 하루 트윗 2개, 읽기는 쓰기의 100배, 트윗 하나 300B, 10%는 사진(200KB)이 붙는다.

**① 쓰기 QPS: 하루 생성량을 초당으로 바꾼다**

```
하루 트윗 수  = 1억 명 × 2개 = 2억 건/일
평균 쓰기 QPS = 2억 ÷ 10만 초 = 2,000 QPS
피크 쓰기 QPS = 2,000 × 2~5배 = 5천~1만 QPS
```

순서는 항상 같다. "하루에 몇 건 생기나"를 먼저 구하고, 하루 = 10만 초로 나눠 초당으로 바꾸고, 트래픽은 균일하지 않으니 피크 배수를 얹는다. 86,400으로 정직하게 나누지 않는 게 요령이다. 10만으로 나누는 건 0 다섯 개를 지우는 것. 2억 → 2,000.

**② 읽기 QPS: 따로 세지 않고 비율로 늘린다**

```
평균 읽기 QPS = 2,000 × 100 = 200,000 QPS
피크 읽기 QPS ≈ 50만 QPS
```

읽기를 왜 비율로 구하냐면, 트윗 하나는 한 번 써지지만 팔로워들의 타임라인에 뜰 때마다 읽히기 때문이다. 이런 읽기 중심 서비스는 읽기:쓰기를 100:1 정도로 가정하는 게 관례다.

**③ 저장량: 건수 × 건당 크기**

```
텍스트: 2억 건 × 300B = 60GB/일 → × 365일 ≈ 22TB/년
사진:   2억 × 10% × 200KB = 4TB/일 → × 365일 ≈ 1.5PB/년
```

곱셈 두 번이 전부지만 주의할 게 하나 있다. 텍스트와 사진(미디어)은 반드시 따로 계산한다. 자릿수가 다르기 때문이다. 연 22TB와 1.5PB는 약 70배 차이인데, 뭉뚱그리면 "용량 문제의 정체는 사실상 사진"이라는 사실이 숫자에서 안 보인다.

**④ 숫자를 단일 장비 용량과 비교한다. 여기까지가 한 세트**

계산 결과를 위의 "단일 장비의 대략적 용량"에 대본다.

- 쓰기 피크 5천~1만 vs DB 한 대 초당 수천 쓰기 → 경계선. 한 대로는 아슬아슬하다
- 읽기 피크 50만 vs DB 한 대 → 자릿수가 두 단계 넘친다. DB가 직접 받을 수 없는 숫자
- 사진 연 1.5PB vs 서버 한 대 저장 공간 → 애초에 DB에 넣을 물건이 아니다

이 비교가 설계의 출발점이 된다. 구체적인 방법은 뒤에서 하나씩 배울 내용이라 맛보기로만 잇자면, 감당 못 하는 읽기는 캐시가 받고, 넘치는 쓰기는 여러 DB에 나눠 담고(샤딩), 사진은 전용 저장소에 따로 두는 식의 결정이 전부 이 세 줄의 비교에서 출발한다. 계산 전에는 "DB 뭐 쓰지?"라는 막연한 질문이, 계산 후에는 "50만 읽기 QPS를 어떻게 받지?"라는 구체적 질문이 된다. **어림 계산은 설계 논의의 과녁을 정한다.**

## 정리

지연과 처리량은 다른 축이고, 응답 시간은 평균이 아니라 p50/p95/p99로 읽으며, 가용성은 9의 개수마다 비용이 곱으로 뛴다. SLO는 이 숫자들을 팀의 의사결정 도구로 바꾼 것. 그리고 설계를 시작하기 전에는 어림 계산으로 논의가 벌어질 자릿수부터 확정한다. 하루 = 10만 초, 메모리:디스크 = 1,000배, 이 둘만 외워도 절반은 된다.
